## Objection 1 (c, and a): `human_set_line_on_another_day` goes red on 2027-01-01, by the plan's own year rule

Task 2 adds the year rule (Review Focus 2: "add the year when `fires_at` falls in a different year
from today") and, in the same task, a test that asserts
`"Reminder set: \"x\" at Thu 22 Oct 14:32:05\n"` for a `fires_at` fixed at 2026-10-22, rendered
through `write_event`, which calls `clock(fires_at, Local::now().date_naive())`. The plan says the
assertion "only holds when today isn't 2026-10-22; that's true from now on". It holds only until
2026-12-31. From 2027-01-01, today's year (2027) differs from 2026, so `clock` takes the third
branch and prints `Thu 22 Oct 2026 14:32:05`; the test fails on every OS in CI, with no code
change, 70 days after merge. This in a repo that pins its toolchain precisely so that "a new Rust
release cannot turn CI red by itself" (`rust-toolchain.toml`): this turns it red by calendar.

Root cause is a spec deviation, not a typo. The spec says "the function is given 'now' as a
parameter so tests can check both cases without the clock". The plan pushes "today" down into
`clock` but leaves `write_event` reading `Local::now()`, and then writes two `write_event`-level
tests (`human_set_line` rebuilt from today's date, and `human_set_line_on_another_day`) that depend
on the wall clock. The rewritten `human_set_line` also has a small midnight race (date taken
before the call, `Local::now()` read inside it).

Fix: thread `today` through (`write_event_at(out, event, json, today)` with `write_event` as the
one-line wrapper, or make `write_event` take it), and pin every human-line test to a fixed
`today`: same day, next day same year, other year. No test should read the clock.

## Objection 2 (b, a): Task 1's tests cannot fail as tests on a machine with a console; they hang, and their stderr assertion passes on the unfixed binary

The `run` helper (`tests/cli.rs:7-16`) is `Command::output()` with no deadline. The measurement
above shows what the unfixed binary does here: it enters the alternate screen, logs the sound
error into that screen, and waits for a key forever. Consequences:

- `assert!(elapsed < Duration::from_secs(5))` is dead code. The binary either exits fast (fixed,
  or no terminal to open) or never exits; `output()` never returns in the second case, so the
  assertion is never evaluated. On a Windows CI runner with a console (UNKNOWN whether
  `windows-latest` has one; this machine does) a regression would surface as the 30-minute
  `timeout-minutes` job kill in `check.yml`, not a named failing test.
- `contains("nope.wav")` does not discriminate: the unfixed binary also writes `nope.wav` to stderr
  (`Error playing sound: cannot open sound file nope.wav`, from `App::tick`), so with a deadline-kill
  added, the old binary would pass that assertion. On Linux CI it only fails because
  `enable_raw_mode` cannot open `/dev/tty`, i.e. for an unrelated reason. The plan's Step 2
  "Expected: FAIL. On Linux, stderr has a terminal error" is that accident; on a Linux or macOS
  developer terminal the old binary takes over the developer's terminal instead.
- The spec's requirement is "before the screen opens". There is an exact oracle for that and the
  plan does not use it: stderr must not contain `\x1b[?1049h` (`EnterAlternateScreen`, written by
  `Tui::init` to stderr).

Fix: give `run` a kill deadline (spawn, poll `try_wait`, kill after N s, fail with a message), and
assert `!stderr.contains("\x1b[?1049h")` plus `starts_with("Error: cannot open")` /
`"Error: cannot decode"`. Then the red step needs no external `timeout` and fails the same way on
all three OSes.

`docs/parking-lot.md` (the versioning decision record the spec points to), `NEXT.md` and

  contain `docs/superpowers/specs/2026-10-23-v0.2.1-polish-design.md` (plan line 11) or the review

- After the release, the decision record lives only in an untracked file on one machine; a fresh

  coupled.
- The three parking-lot entries this batch ships (`docs/parking-lot.md` lines 23-25 set line,
  29-31 `-s` check, 63-65 licence) are never removed or marked done. The project rule is to read
  the parking lot when scoping the next piece of work; in six months it still advertises three

- Beads: the epic has 5 children = 1 closed (`.1`, dropped) + 1 closed by Task 4 Step 7 (`.5`) +
  3 with no close step (`.2`, `.3`, `.4`). Putting the id in a commit body does not close a bead.

  either outcome is wrong).

Fix: a Task 0 that commits the spec, plan, both reviews and the parking-lot edit to `main` before
branching; `bd close` in each of Tasks 1-3; delete or strike the three parking-lot entries in
Task 4 Step 3's handoff commit.
