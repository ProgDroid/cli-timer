## Objection 1 (b, an assumed requirement): no known user receives the main fix

The intent says: "a fix to the skill alone should reach users without a crate release". Nothing in
the repo shows that there is any such user, or any such fix.

- **The developer gains nothing.** `known_marketplaces.json` records the `cli-timer` marketplace as
  `"source": "directory", "path": "G:\\rustDev\\cli-timer"`. The docs say a relative-path plugin in
  a local-path marketplace "loads its current source files at every session start, whatever its
  version string says", and NEXT.md "Things you might notice" says the same. The only plugin install
  the evidence shows is unaffected by item 1.
- **No other plugin user is evidenced.** The repo is public, with 0 stars and 0 forks. The clone
  API reports 186 clones from 54 unique cloners over 14 days, 171 of them (47 unique) on 2026-10-22.
  That was the release day, when check.yml ran on three OSes and release.yml built four archives. CI
  runners can explain that spike, so it does not show any plugin users. dotman (in dotfiles) runs
  `cargo install --git`, which installs the binary and not the plugin. So the number of other plugin
  users is UNKNOWN, and no evidence shows even one.
- **No skill-only fix has happened yet.** `git diff --stat 87ede31 HEAD` (where 87ede31 is v0.2.0)
  shows `{skills => plugin/skills}/timer/SKILL.md | 0`, a pure rename. The skill has had no edits
  since the release.
- **"Ships on push" is really "ships on the user's next manual update".** The docs give the
  auto-update default as "off for every other marketplace", and the spec agrees ("auto-update is
  off"). So a GitHub user gets the fix only when they run `claude plugin update`. They have no
  reason to run it, because nothing tells them a fix exists. A version bump at least makes a
  release visible. It is also UNKNOWN whether `claude plugin update` refreshes the marketplace
  clone first: the reference says it moves to "the latest version its marketplace offers", and
  says nothing about a refresh. If it does not, the user also needs
  `claude plugin marketplace update`.

So item 1 replaces a working coupling, plus a test that enforces it, with new machinery. The gain
goes to a user population of size UNKNOWN, possibly zero, and only for a change that has not
happened once.

**Simpler (a), for most of the value:** ship items 2, 3 and 4 as 0.2.1, and leave the plugin
versioning alone until a real skill-only fix exists. When one comes, cut a patch release. The
release path is already one dry run and one tag push (CLAUDE.md, NEXT.md Housekeeping). If the
coupling must go now anyway, the one-line change (drop `version`, plus a test that no `version` key
exists) gets the whole stated benefit. It does so without the second test, which promises something
it cannot check (see Objection 2).

## Objection 2 (the fixed check: an unsupported implicature that displaces the weakest objection)

Spec section 1, "What changes": "the minimum version in `SKILL.md` ... is no higher than
`CARGO_PKG_VERSION`, so `main` never asks for a binary that doesn't exist."

- The two facts: the minimum is at most `CARGO_PKG_VERSION`, and `CARGO_PKG_VERSION` is the version
  in `Cargo.toml` on `main`.
- What a reader infers: any user who reads the skill on `main` can get a binary that satisfies it.
- Why neither fact establishes that: `CARGO_PKG_VERSION` on `main` is not the same thing as a
  released version. The parking-lot entry this item closes names the gap itself ("between bump
  and tag a fresh install can get a skill that expects an unreleased binary"). The spec's release
  step ("bump `Cargo.toml` only") leaves that gap in place. The test passes in both of these cases:
  - **The minimum is raised early.** Cargo goes to 0.3.0 on `main` before the tag, so the test
    allows a skill that says "0.3.0 or newer". The releases page has no 0.3.0, so the
    release-archive route in SKILL.md section 1 cannot satisfy it. Only `cargo install --git` can.
  - **The minimum is not raised.** This is the common case. A new flag lands on `main` and the
    skill starts using it, but the skill still says 0.2.0, so the test still passes. A user on the
    released 0.2.0 binary passes the skill's check and then gets a usage error (exit 2).
- A second implicature in the same paragraph. "That is covered by the skill's existing '0.2.0 or
  newer' check ..., raised when the skill starts needing something newer" puts the check next to
  the risk and implies the check prevents the risk. It does not: someone has to raise the floor by
  hand, in prose. That is the "keep them coupled with a written rule" approach the developer
  rejected, moved to a different file.
- A third, in section 1 "Facts". "`cargo install --git` also installs `main`, so the binary and the
  skill both track `main`" implies the user's binary and skill are in step. They are not. Each one
  moves only when its own command runs (`cargo install` or `claude plugin update`), and
  release-archive users never track `main` at all.

Verdict: the second test gives false comfort. Either drop it, or make it check a fact that actually
supports the inference. One example: the minimum is no higher than the newest `vX.Y.Z` tag, using
`git describe --tags --abbrev=0` in the test or a version list committed at release time.

## Objection 3 (c, a constraint it will hit within 6 months): the roadmap couples plugin and binary again

The parking lot's two largest entries are interface changes between the plugin and the binary:

- **MCP server mode** ships a `.mcp.json` in `plugin/` that launches `cli-timer mcp`.
- **Detached reminders** add `start/list/cancel/stop`, and SKILL.md section 3 would have to change
  to use them.

With no `version`, every user who runs `claude plugin update` gets the new plugin on the next push,
whatever binary they have. The only guard is the skill's prose floor, which the agent reads when it
runs the skill. A `.mcp.json` server starts with no skill involved, so on a 0.2.x binary it fails as
an MCP server that won't start, before any version check can run. The design removes the one
mechanism that tied "this plugin" to "this binary", just before the roadmap needs that tie back.
At that point the choice is between restoring a `version` (this change undone) and building the
"independent plugin semver" machinery the spec rejected.

The same push-equals-update rule produces noise today. The repo has 19 commits. 10 have a `prefix:` subject:
6 `handoff:`, 2 `bd:`, 1 `bd init:` and 1 `chore:` (6 + 2 + 1 + 1 = 10). The other 9 are older
free-form subjects. So 9 of the 10 prefixed commits are `handoff:` or `bd:` bookkeeping, and that
share will grow under the session routine. If the version is the marketplace HEAD SHA
(see below), every one of those mints a new plugin version with the same skill bytes. A user who
turns auto-update on sees "Plugin updated" after each NEXT.md commit.

## Smaller findings (not objections)

- **The date example is a Saturday.** Section 3's example `Fri 24 Oct 14:32:05` is impossible in
  2026: 2026-10-24 is a Saturday (`py`: `date(2026,10,24).strftime('%a')` = `Sat`). The existing
  output tests build times in 2026 (`at()` uses 2026-10-22). If a test copies the spec's string,
  either the test fails or the weekday logic is wrong. Use `Sat 24 Oct` or another date.
- **Test counts in NEXT.md go stale.** NEXT.md "How to run" says 157 tests (156 on Windows).
  Item 1 adds one net test, and item 3 adds at least two, so the handoff must update those numbers.
  The spec does not mention it.
- **NEXT.md's Housekeeping line** ("bump `version` in `Cargo.toml` and
  `plugin/.claude-plugin/plugin.json`") must change in the same commit. The spec covers this.
- **The SKILL.md minimum test** parses the prose "You need **X.Y.Z or newer**" (SKILL.md line 28,
  one occurrence). A wording edit then breaks a test. That is fine if the failure message says
  why.
- **After this change the developer's own install key changes.** `installed_plugins.json` records
  `cli-timer@cli-timer` as `version: 0.2.0`, `installPath ...\cache\cli-timer\cli-timer\0.2.0`.
  Without a manifest `version`, a directory source that is a git repo gets a computed version (the
  docs' `unknown` applies only when neither directory is a git repo). Loading in place should make
  that harmless, but nobody has checked it. Check with a restart and `/plugin` after the change.
